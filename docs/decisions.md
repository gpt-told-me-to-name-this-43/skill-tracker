# Технические решения (Decisions)

Этот документ является источником правды для тестирования (наравне с Acceptance Criteria). При спорном поведении сверяться с этим файлом.

## Общие архитектурные решения
1. **Единый тип ID:** Во всех сущностях проекта используется единый тип идентификаторов.
2. **Пустые данные:** Если у пользователя нет навыков, запрос `GET /users/{id}/skills` возвращает `200 OK` и пустой список `[]`. Нулевые агрегаты прогресса (`skills_count`, `average_level`, `total_experience`) возвращает `GET /users/{id}/progress`.
3. **Role и RBAC:** Сущность role существует, однако Role-Based Access Control (RBAC) реализуется отдельным механизмом.
4. **Первый admin:** Создаётся не через ручку регистрации, а напрямую (скриптом или сидированием БД).
5. **Справочник навыков:** Ограничен. Попытка создать дубль (включая другой регистр букв) возвращает `409 Conflict`.
6. **Тестирование:** Автоматические тесты (JUnit 5) вынесены в отдельную задачу. QA проверяет только поведение, **наблюдаемое снаружи** (API/UI). Внутренние механизмы (вызовы хуков, структура кода) руками не проверяются.
7. **Коды ошибок:** Применяются стандартные HTTP коды (400, 401, 404, 409, 422). Логин при 401 ошибке не раскрывает, что именно было неверным (email или пароль).

## Логика Experience и Уровней
1. **Расчет уровней (Формула):** 
   - `exp=0` → level=1, progress=0
   - `exp=50` → level=1, progress=50
   - `exp=99` → level=1, progress=99
   - `exp=100` → level=2, progress=0
   - `exp=200` → level=3, progress=0
   - `exp=250` → level=3, progress=50
   *Важно: Фронтенд и QA не должны считать формулу сами как источник правды. Значения берутся из ответа API.*

2. **Особенности Experience:**
   - XP — это метрика участия, а не качества выполнения.
   - Ревьюер XP не получает.
   - Задача без наград — полностью допустима.

## Workflow задач
Переход в `done` разрешён **только из `review` и только после апрува** (`PATCH /tasks/{id}/approve`).
Попытка перевести задачу в `done` из другого статуса или без апрува возвращает `400`.
Все кейсы ниже, где выполняется `PATCH status=done`, подразумевают предусловие: задача в `review` и апрувнута.

## Edge cases Experience (У1-У6)
- **У1:** `done` без исполнителя (задача в `review`, апрувнута). Задача закрывается (200), XP не начисляется, experience-log пуст.
- **У2:** Переназначение после `done`. XP остаётся у старого исполнителя. Это **НЕ баг**, а фича.
- **У3:** Транзакционность (откат статуса при падении начисления). Руками невозможно проверить, покрыто автотестом в Experience-issue (лид).
- **У4:** Идемпотентность (наблюдаемая часть). Повторный PATCH `status=done` по той же задаче не задваивает XP, лог не растет. Вызов хука ровно один раз проверяется автотестом.
- **У5:** Задача без наград. Закрытие проходит, XP не начисляется.
- **У6:** Исполнитель без связи UserSkill. После закрытия задачи с наградой, навык автоматически появляется в профиле с уже начисленным XP.
